# Mini NPU Simulator

`Mini NPU Simulator`는 `data.json`에 저장된 패턴과 필터를 읽어,
각 패턴이 `Cross` 또는 `X` 중 어느 쪽에 더 가까운지 MAC(Multiply-Accumulate) 점수로 판정하는 프로그램입니다.

---

## 1. 실행 방법

### 1-1. 준비 파일
아래 파일들이 같은 폴더에 있어야 합니다.

- `main.py`
- `data.json`

### 1-2. 실행
터미널에서 아래 명령을 실행합니다.

```bash
python main.py
```

### 1-3. 메뉴
실행 후 다음 메뉴가 표시됩니다.

```text
Mini NPU Simulator
1) 사용자 입력(3×3)
2) data.json 분석
입력 방식 선택 (1/2):
```

- `1` : 사용자가 직접 3×3 필터 A/B와 패턴을 입력
- `2` : `data.json`을 읽어서 자동 분석

---

## 2. 프로그램 동작 방식

이 프로그램은 두 가지 모드로 동작합니다.

### 2-1. 사용자 입력 모드
- 3×3 필터 A, 필터 B, 패턴을 직접 입력합니다.
- 패턴과 각 필터의 MAC 점수를 비교합니다.
- 더 큰 점수의 쪽으로 판정합니다.

### 2-2. JSON 분석 모드
- `data.json`을 읽어 여러 테스트 케이스를 자동 판정합니다.
- 각 케이스의 정답(`expected`)과 예측(`predicted`)을 비교합니다.
- 결과를 `result.json`으로 저장합니다.

---

## 3. 판정 기준

판정은 다음 규칙으로 수행됩니다.

- `Cross` 점수 > `X` 점수 → 예측 = `Cross`
- `X` 점수 > `Cross` 점수 → 예측 = `X`
- 두 점수가 거의 같으면 → `UNDECIDED`  
비교 기준은 `EPS = 1e-9`입니다.

### 부동소수점 오차와 EPS
MAC 점수는 소수 계산을 포함하므로, 계산 순서와 부동소수점 오차 때문에 아주 작은 차이가 생길 수 있습니다.  
이 차이가 실제 의미 있는 차이인지, 단순한 계산 오차인지 구분하기 위해 허용 오차 `EPS`를 사용합니다.
데이터의 크기나 값의 범위가 더 커지면, `EPS`는 상황에 맞게 조정할 수 있습니다.
값 차이가 매우 큰 데이터는 더 큰 EPS가 필요할 수 있고, 아주 정밀한 비교가 필요하면 더 작은 EPS를 사용할 수 있습니다.

### 왜 `1e-9`인가?
- 파이썬 함수 math.isclose(a, b)에서 상대오차 기본값은 rel_tol=1e-09를 사용하기에 이를 준용하여 지정하였습니다.

### 판정 방식

MAC 점수는 정규화된 확률이 아니라, 입력과 필터의 원소 곱을 누적한 원시 합산값입니다.
따라서 절대값보다는 두 점수의 상대적 크기를 기준으로 판정합니다.

- `abs(a - b) < EPS` 이면 동점으로 처리합니다.
- `EPS`보다 크면 더 큰 쪽을 결과로 선택합니다.

### 동점처리
- `UNDECIDED`는 PASS/FAIL과 별도로 집계되며, 실패 수에는 포함되지 않습니다.
- 동점(`UNDECIDED`)은 판정 불가 상태이며, 오판정 실패와는 구분됩니다.

## 4. `data.json` 형식

현재 코드는 다음 구조를 기준으로 동작합니다.

### 4-1. 최상위 구조
```json
{
  "meta": {
    "version": "1.0",
    "type": "json"
  },
  "filters": { ... },
  "patterns": { ... }
}
```

### 4-2. `filters` 형식
필터는 보통 다음과 같이 저장됩니다.

```json
{
  "filters": {
    "size_5": {
      "cross": [[...], [...], [...], [...], [...]],
      "x": [[...], [...], [...], [...], [...]]
    },
    "size_13": {
      "cross": [[...], ...],
      "x": [[...], ...]
    }
  }
}
```

### 4-3. `patterns` 형식
패턴은 다음과 같이 저장됩니다.

```json
{
  "patterns": {
    "size_5_1": {
      "input": [[...], [...], [...], [...], [...]],
      "expected": "x"
    },
    "size_5_2": {
      "input": [[...], [...], [...], [...], [...]],
      "expected": "+"
    }
  }
}
```

### 허용되는 입력 키
코드는 다음 키를 패턴 행렬로 인식합니다.

- `pattern`
- `input`
- `data`
- `matrix`

### 허용되는 라벨
코드는 라벨을 내부적으로 정규화합니다.

| 입력 라벨 | 내부 표준 라벨 |
|---|---|
| `+` | `cross` |
| `cross` | `cross` |
| `c` | `cross` |
| `plus` | `cross` |
| `x` | `x` |
| `diag` | `x` |

## 9. 결과 리포트

이 프로그램의 결과 리포트는 단순한 성공/실패 목록이 아니라, 판정 품질과 처리 성능을 함께 보여주는 구조입니다.  
아래는 결과 해석 시 확인해야 할 핵심 요소입니다.

1. 전체 테스트 수는 `patterns`에서 실제로 분석한 케이스의 개수입니다.  
2. 통과 수는 `expected`와 `predicted`가 일치한 케이스 수입니다.  
3. 실패 수는 라벨이 다르거나, 분석 중 예외가 발생한 케이스까지 포함해 집계됩니다.  
4. 동점 수는 `Cross`와 `X` 점수가 `EPS` 기준으로 거의 같아 `UNDECIDED`가 나온 경우입니다.  
5. 실패 비율은 전체 테스트 수 대비 실패 수의 비율로 계산됩니다.  
6. 평균 시간은 각 케이스의 MAC 계산 시간을 기준으로 계산됩니다.  
7. 실패가 발생한 경우, 먼저 `expected` 라벨이 `cross` 또는 `x`로 정상 정규화되었는지 확인해야 합니다.  
8. 다음으로 `filters` 안에 해당 size의 `cross`, `x` 필터가 정확히 존재하는지 확인해야 합니다.  
9. 패턴과 필터의 크기가 다르면 비교 자체가 불가능하므로 실패로 처리됩니다.  
10. 패턴이 정사각 행렬이 아니거나, 행 길이가 모두 같지 않으면 예외가 발생할 수 있습니다.  
11. 부동소수점 오차가 매우 작은 경우에는 `EPS = 1e-9` 때문에 동점으로 처리될 수 있습니다.  
12. 따라서 아주 비슷한 점수는 실제 차이보다 계산 오차로 간주되어 `UNDECIDED`가 될 수 있습니다.  
13. 실패가 0개인 경우에는, 정답 라벨 정규화가 올바르게 수행되었고 필터 매칭도 정확했음을 의미합니다.  
14. 또한 `EPS` 정책 덕분에 수치적으로 거의 같은 경우를 안정적으로 동점 처리했기 때문에 불필요한 오판정이 줄어듭니다.  
15. 즉, 실패 0은 단순히 운이 좋았다는 뜻이 아니라, 입력 구조, 정규화 정책, epsilon 정책이 함께 잘 맞아떨어졌다는 의미입니다.

### 실패가 0개일 때의 해석
실패가 0개라면 다음 두 가지가 특히 중요합니다.

- **정규화 정책**: `"+"`, `"Cross"`, `"cross"`가 모두 같은 기준으로 처리되었는지
- **epsilon 정책**: 수치 차이가 너무 작은 경우 `UNDECIDED`로 안정적으로 처리되었는지

이 두 정책이 제대로 동작하면, 데이터가 조금 달라도 판정 결과가 일관되게 나올 가능성이 높아집니다.

## 10. `normalize_label` 함수를 분리한 이유와 장점

라벨 정규화는 입력값을 내부 기준으로 통일하는 작업입니다.  
이 기능을 `normalize_label` 함수로 분리한 이유는 다음과 같습니다.

### 장점
- **중복 제거**: `expected`, `label`, 필터 키 등에서 같은 정규화 규칙을 재사용할 수 있습니다.
- **유지보수 용이**: 새 라벨이 추가되더라도 한 곳만 수정하면 됩니다.
- **테스트 용이**: 정규화 규칙만 따로 검증할 수 있어 오류를 찾기 쉽습니다.
- **일관성 확보**: 사용자 입력과 JSON 입력을 같은 기준으로 처리할 수 있습니다.

### 예시
| 입력 라벨 | 내부 표준 라벨 |
|---|---|
| `+` | `cross` |
| `cross` | `cross` |
| `c` | `cross` |
| `plus` | `cross` |
| `x` | `x` |
| `diag` | `x` |

즉, `normalize_label`은 입력 형식이 달라도 내부에서는 같은 기준으로 비교할 수 있게 해주는 역할을 합니다.

## 11. 모드별 동점 처리

두 모드는 모두 동일한 `EPS` 기준으로 동점을 판정합니다.  
차이는 판정 기준이 아니라 출력 라벨과 사용 목적입니다.

### 사용자 입력 모드
- A와 B 중 어느 쪽이 더 큰지 비교
- 동점이면 `UNDECIDED`

### JSON 분석 모드
- `Cross`와 `X`를 비교
- 동점이면 `UNDECIDED`
- 정답(`expected`)과 비교하여 PASS/FAIL 기록

즉, 두 모드 모두 점수 차이가 매우 작으면 `UNDECIDED`로 처리합니다.

## 12. 새 라벨 추가 방법

예를 들어 `Diagonal` 같은 새 라벨을 추가하려면 아래 순서로 수정해야 합니다.

### 12-1. 정규화 함수 수정
- `normalize_label()`에 새 라벨을 인식하도록 추가합니다.
- 예: `"Diagonal"`, `"diag"` 등을 내부 표준 라벨로 매핑합니다.

### 12-2. 판정 로직 수정
- 라벨이 `Cross`와 `X`만 있는 구조라면, 새 라벨에 대한 필터 선택 및 비교 규칙을 추가해야 합니다.
- 예측 결과를 반환하는 분기에도 새 라벨을 반영해야 합니다.

### 12-3. 출력 메시지 수정
- 콘솔 출력, `result.json`, README 예시에서 새 라벨명이 일관되게 표시되도록 수정합니다.

### 12-4. 테스트 데이터 수정
- `data.json` 예시와 테스트 케이스에 새 라벨을 포함합니다.
- 정규화 전/후 값이 올바르게 처리되는지 확인합니다.

즉, 새 라벨 추가는 **정규화 → 판정 → 출력 → 테스트** 순서로 함께 반영해야 합니다.

## 13. CPU와 NPU의 병목 차이

이 프로그램은 NPU 개념을 단순화한 시뮬레이터입니다.  
실제 하드웨어 관점에서 CPU와 NPU는 병목이 생기는 지점이 다릅니다.

### CPU의 특징
- 일반적으로 **직렬 처리 비중**이 큽니다.
- 분기, 제어 흐름, 다양한 연산을 유연하게 처리합니다.
- 하지만 대량의 같은 연산을 반복할 때는 계산 효율이 제한될 수 있습니다.

### NPU의 특징
- 같은 연산을 많이 반복하는 작업에 적합한 **병렬 처리 구조**를 가집니다.
- MAC처럼 반복되는 곱셈-덧셈 연산을 빠르게 처리하도록 설계됩니다.
- 다만 데이터 이동, 메모리 대역폭, 입출력 정렬이 병목이 될 수 있습니다.

### 병목 지점
- **CPU 병목**: 연산 순서, 반복 처리, 캐시 효율
- **NPU 병목**: 데이터 공급 속도, 메모리 전송, 병렬 자원 활용률

이 프로젝트에서는 MAC 계산 자체에 집중하지만, 실제 NPU 설계에서는 계산 속도뿐 아니라 **데이터 이동 비용**과 **병렬 활용률**도 중요합니다.

## 14. 복잡도와 최적화 관점

### 시간 복잡도
- 한 패턴의 MAC 계산은 `O(N²)`
- `M`개의 테스트를 처리하면 전체는 `O(M × N²)`

### 공간 복잡도
- 입력 행렬과 필터를 저장하므로 `O(N²)`

### 최적화 관점
다음과 같은 최적화가 도움이 될 수 있습니다.

- **블록화(blocking)**: 큰 행렬을 작은 단위로 나누어 캐시 효율을 높임
- **스트라이드 접근 최적화**: 메모리 접근 패턴을 개선해 불필요한 캐시 미스를 줄임
- **평탄화(flatten) 연산 사용**: 2D보다 단순한 1D 접근으로 오버헤드를 줄일 수 있음
- **불필요한 복사 감소**: 중간 배열 생성을 줄여 메모리 사용량을 낮춤

이러한 최적화는 데이터 크기가 커질수록 효과가 더 커집니다.
